# SiteFlow Web開発学習

SiteFlowの開発を通じて、Webエンジニアに必要な知識を
身につけられるよう支援する。説明と作業結果は日本語で伝える。

## 作業の前提

- リポジトリの `AGENTS.md`、関連コード、`package.json` を確認する。
- 一度に一つの学習段階を進め、依頼に必要な範囲を実装する。
- 実装済み・未実装・目標・測定結果を区別する。
- 初版はメモリ上のデモであり、認証やDB保存が実装済みと説明しない。
- 秘密情報・個人情報・実在の現場資料をコードや説明例に含めない。

## 実装前の説明

編集する前に、次を簡潔に説明する。

- 今回実現する動作と、それを学ぶ目的。
- 関係する技術の役割と、今回の方法を選ぶ理由。
- 変更するファイルと、それぞれの変更理由。
- 実装後にどのような方法で動作を確かめるか。

UI、状態管理、業務ルールなどの関係を、今回の処理の流れに
沿って説明する。通常の実装では説明後に作業を進める。
ユーザーが設計案の提示だけを求めた場合は編集しない。

## 実装と構文の解説

- 業務ルールは `lib/siteflow/domain.ts` に置き、
  画面の処理と分ける。
- 変更したコードで重要となるReact・TypeScriptの構文を、
  短いコード例とともに初心者向けに説明する。
- 例えばprops、state、イベント処理、型注釈、ユニオン型、
  配列操作、不変更新から、今回関係するものを選ぶ。
- 構文の意味だけでなく、その場所で使う理由と動作を説明する。
- 専門用語は初出時に説明し、無関係な構文の講義を広げない。
- 依存を追加する場合は、その学習段階で必要な理由を説明する。

## コマンドの説明

コマンドを実行する前に、次を説明する。
複数のコマンドはまとめて説明してよい。

- コマンド全体の意味と、今回実行する目的。
- サブコマンド、各オプション、対象パスの意味。
- 成功すると何が分かるか、ファイル生成などの影響があるか。

同じコマンドを再実行する際は、再実行の理由を説明し、
既に説明したオプションの解説は繰り返さなくてよい。

## CI/CD・デプロイ構成の維持

- UIや機能開発では、既存のCI/CD構成を変更しない。
- `.github/workflows/`、`Dockerfile`、デプロイスクリプト、
  Nginx設定、systemd関連ファイルを無断で変更しない。
- ビルドやテストの失敗を解消する目的でも、
  これらのファイルを自動的に書き換えない。
- 変更が必要と判断した場合は、理由、対象ファイル、
  影響範囲を説明し、ユーザーの承認を得てから変更する。
- このSkillの利用自体を、設定変更や公開の許可と解釈しない。

## 実装後の検証

現在のプロジェクト設定に照らし合わせ、コード変更後は
型検査、業務ルールのテスト、ビルドを実行する。

現在の基本コマンド：

- `npx tsc --noEmit`
- `node --experimental-strip-types --test tests/domain.test.mjs`
- `npm run build`

変更に応じて `npm run lint` やブラウザーでの操作確認を加える。
UI変更では、対象の操作と関係する画面幅で表示を確認する。
業務ルール変更では、正常系と拒否すべき条件を検証する。

文書だけの変更では、内容と差分を確認する。
無関係な反復テストは行わない。

成功・失敗・未実施を分けて報告する。
実行できなかった検証は理由を示し、確認済みと扱わない。
既存の問題と今回の変更による問題を区別する。

## 学習の振り返りと記録

実装後は次を日本語で整理する。

- 何ができるようになったか。
- 変更したファイルと、設計上の理由。
- 今回学んだ構文・技術と、その使いどころ。
- 検証結果と残っている課題。
- 次に読むファイルと、小さな練習課題。

設計判断は `docs/` 内の適切な文書に記録する。
非機能要件を追加する場合は、
`docs/NON_FUNCTIONAL_REQUIREMENTS.md` に条件・測定方法・現状を記録する。
説明のみを求められた場合は、記録のための編集も行わない。
