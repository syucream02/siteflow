## 最新：アーカイブ・専用閲覧・担当調整付き復元（2026年11月15日）

分離APIで保管と復元を追加。本体画面は未接続。以下の各段階は当時の記録として読む。アーカイブと完了/物理削除は別で、状態・進捗・過去履歴を自動変更しない。

追加した受付：

- `POST /api/teams/:teamId/projects/:projectId/archive`：本文expectedVersionのみ。現在所属する管理者/主副担当が操作でき、完了以外も保管可能。archivedAtをサーバー時刻、共通versionを+1にする。
- `POST /api/teams/:teamId/projects/:projectId/restore`：本文expectedVersionと、任意でprimaryUserId/supportUserIdsの両方。担当を選び直す場合は現在所属する同じチームの主担当1人/副担当0〜50人を指定し、主副重複を拒否する。省略時は元の担当を使う。変更後の全担当が現在のadmin/memberでない場合は409 INACTIVE_ASSIGNEES。DONEの復元でも確認する。
- `GET /api/teams/:teamId/archived-projects`：保管中だけを納期→IDの昇順、通常20/最大50件、UUID cursorで取得。通常一覧と目印の対象を分離。項目は通常一覧にarchivedAt/versionを追加したもの。0件は200空配列。復元されたcursorは400となり、最初から取得する。
- `GET /api/teams/:teamId/archived-projects/:projectId`：基本情報/版/保管日時/主担当/作成時の記録を取得。主担当には復元で選ぶためのuserIdと現在所属フラグを含め、メールやセッションは返さない。
- 同じ保管詳細の下に`/support-members`、`/progress-history`、`/assignment-history`のGETを追加。従来のページ分割とチーム/案件境界を使い、親案件も保管中に限定。保管用副担当にはuserIdを追加。履歴自体の更新/削除は公開しない。

通常の一覧/詳細/関連取得は保管案件を除外したまま。基本編集/担当/進捗/状態変更も保管中は404。保管中の内容確認は専用のGETから行う。通常のAPIの既存の応答項目は維持する。

保存処理は`project-archive-service.ts`へ分離。事前に担当IDと版だけ読み、本人/旧担当/選び直した担当の所属→案件の順でロックする。ロック後の現在の権限と共通version、事前版を再確認。事前値だけで保存を判断しない。所属なし403、無権限403、対象チーム内にない/不明案件404、古い版409。Host/Origin/セッションも確認する。

本文はJSON必須415、32768バイト上限413、expectedVersionは整数1〜2147483646。不正入力/余分な属性/検索条件400、POST以外405。操作はURLから決め、archivedAtやstatusを本文から受け付けない。復元で担当の片方だけの指定や重複は400。非保管案件に担当指定付きで復元しようとすると409 PROJECT_NOT_ARCHIVEDで、担当だけを更新する抜け道にしない。

200はproject:{id,version,archivedAt}とchangedを返す。最新の版で既に同じ保管状態ならchanged:false、版/日時/履歴を維持。古い版なら同じ状態でも409。復元はarchivedAt:nullへ戻すだけで、状態と進捗を保持する。

復元で担当を選び直した場合、人物upsert→保管解除と主担当/版更新→副担当追加/解除→担当差分履歴を同じtxで保存する。保持した関連行や旧人物/履歴は消さない。担当履歴の名前はDB上の保存時の値、変更者はセッション本人。アーカイブ/復元だけの場合は担当/進捗履歴を増やさない。保管操作自体の監査履歴・実行者の永続記録は未実装で、archivedAt/versionのみ。

検証：業務40件、API/DB統合96件（HTTP81＋サービス直接15）成功。追加はHTTP8件＋直接3件。保管→専用の一覧/詳細/担当/履歴→復元がHTTPでつながり、DBの案件/人物/履歴と進捗/状態を保持。保管中の通常取得/編集拒否、専用取得のページ分割/0件/カーソル境界/読み取り専用、権限/元所属/本文等を確認した。元所属の主担当または副担当の復元拒否、担当の選び直しと差分履歴、DONEを保持した復元も確認。

アーカイブと基本/担当/進捗/状態の同版HTTP同時5操作は一方だけ成功。アーカイブ後は通常の対象外になるため、残りは409または404。HTTP同版同時復元は一方200/他方409。別の主副担当の同時保管はサービス直接で一方のみ成功。事前読取後の編集割り込みも409。全競合や高負荷、別人のHTTP並行通しの保証ではない。

本体/検証API型検査・ESLint・本体ビルド成功。型キャッシュはビルド前へ復元。旧DB制約13件は今回は再実行なし。DB定義/マイグレーション/依存/CI/CD/Dockerfile/デプロイ設定は変更なし。

## 分離した認証APIの追加検証（2026年11月14日）

Better Auth 1.7.23のPrismaアダプターを、統合候補を適用済みの専用DBへ接続した。

```text

                             ↓

GET 本人確認 ← Cookieを送る → DBのSessionを確認
POST ログアウト → Sessionを削除 → 旧Cookieも使えなくなる
```

### 登録の仮仕様

- 必須はname（前後空白を除く1〜200コードポイント）、dueDate（1000〜9999年、実在するYYYY-MM-DD、過去日も可）、primaryUserId（現在のチーム所属者のUUID）。
- supportUserIdsは省略時空配列、最大50人。UUIDは小文字へ正規化し、大文字小文字違いも含む重複と主担当との重複を拒否する。作成者が主担当とは別でも、副担当を兼ねてもよい。
- 任意項目はcode最大100、clientName最大200、summary/notes最大2000コードポイント。省略/null/空白はnull。概要・備考は改行/タブ可、単行項目は制御文字を拒否する。
- 作成者・ID・progress=0・status=NOT_STARTED・version=1はサーバーで決定し、これらの追加指定は400。登録後の進捗入力・完了条件・状態遷移の仕様は確定していない。
- Origin一致、application/json、JSON本文32768バイト以内を要求。チーム作成は従来の4096バイト以内を維持し、本文読取りをjson-body.tsへ共通化した。未認証401、未所属チーム403、不正入力や担当400、Content-Type415、過大本文413。

### 保存と担当記録

project-service.tsが単一のPrismaトランザクションで処理する。対象チームの本人・主担当・副担当の所属行を、パラメーター化したSELECT ... FOR UPDATEで読みロックする。現在のadmin/memberかを再確認してから、TeamParticipantを(teamId,userId)でupsertする。
人物IDを使って案件と副担当を保存し、作成者の現在名をcreatedByNameSnapshotへ記録。初回の主担当設定はPRIMARY_CHANGE（変更前null）、副担当は各SUPPORT_ADD（変更前null）を同じtxで保存する。進捗はまだ変更していないため、初期の進捗履歴は作らない。
登録時の初期履歴の追加であり、登録後の担当変更APIを実装した意味ではない。既存の人物IDは再利用し、過去の参照を付け替えない。

所属行をロックするのは、確認から保存までの間に同じ行を削除・変更されるのを待たせるため。保存後に解除される。保存後の未完了担当・最後の管理者の所属解除拒否は別の業務APIが必要で、今回は未実装。
SQLはPrisma.sql/Prisma.joinで値をバインドし、入力文字列をSQL文へ連結しない。ロック対象は最大52人（本人＋主担当＋副担当50）。人物のupsertは必要な人数分行うが、一覧取得のJSループ内へDB呼出しは追加していない。実SQL回数・大人数の性能は未測定。

変更ファイルはdomain.ts（型・登録入力/許可のルール）、project-service.ts（新しい保存サービス）、json-body.ts（2つの作成APIで共用する本文読取り）、auth-check.ts（受付/候補/保存呼出し）、検証用tsconfigと2テスト。integrated.prismaは古い実装状況コメントだけを訂正し、定義・マイグレーションは変えていない。
canCreateProjectは現在のadmin/memberへ作成を許可し、編集や担当変更の許可には流用しない。unknown入力を検証してCreateProjectInputへ整え、HTTPとDB保存の役割を分ける。
