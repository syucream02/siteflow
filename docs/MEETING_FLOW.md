### 調査案：大量履歴の取得件数・実行計画・索引（未測定）

現在の比較元取得は対象案件をIN条件で限定し、案件ごとにROW_NUMBERの先頭1件だけ返すため、返却は会議対象の最大500件。ただし過去の会議数・確認/取消記録数には上限がなく、DB内部の走査・並べ替え件数は500件に限定されない。10秒取得は会議の読み取りトランザクション内で動くため、遅い取得が確認操作の待ち時間へ影響する可能性も確認する。

検証専用DBだけで、次の順に確認する。今回は方法の整理のみで、大量データ投入・実行計画取得・索引変更は実施していない。

1. `SELECT DATABASE();` で接続先を検証設定と照合してから、件数を数える。これは現在のDB名を読むだけで、外部へ転記しない。
2. 下記COUNTは確認履歴の実件数を返す。大規模時は読み取り負荷がある。チーム別/対象案件別にもアプリと同じパラメーターで絞り、返却件数と走査候補件数を区別する。
3. SHOW INDEXで実DBの索引と列順を読み、設計ファイルと一致するか確認する。FROMは対象テーブル。索引を作る操作ではない。
4. `meeting-service.ts` と同じ比較元SELECTに `EXPLAIN FORMAT=JSON` を付け、選ばれた索引・結合順・推定走査件数・一時表・並べ替えを見る。FORMAT=JSONは結果の表示形式。
5. その後、PC内の隔離データで `EXPLAIN ANALYZE FORMAT=TREE` を付けて実行時間・実走査件数・繰り返し回数を測る。ANALYZEはSELECTを実際に実行するので負荷がある。大量実行は一度に行わず、1千→1万→5万確認記録へ段階的に増やす計画とする。各段階で対象1/100/500案件、同時進行/取消/記録なしを含めて確認し、テストデータだけを回収する。

```sql
-- 実行方法の案。接続先が検証専用DBだと確定した後だけ使用する。
SELECT COUNT(*) AS meetingCount FROM Meeting;
SELECT COUNT(*) AS confirmationCount FROM MeetingConfirmation;
SELECT COUNT(*) AS validConfirmationCount FROM MeetingConfirmation WHERE revokedAt IS NULL;
SHOW INDEX FROM Meeting;
SHOW INDEX FROM MeetingProject;
SHOW INDEX FROM MeetingConfirmation;
```

ソース上の既存索引は `Meeting(teamId, startedAt, id)`、`MeetingProject(teamId, projectId)`、`MeetingConfirmation(teamId, entryId, confirmedAt, id)` と各主キー/一意制約。endedAt・revokedAtの絞り込み、ROW_NUMBERのソートで実際にどう使われるかは実行計画で確認する。返却が少ないことだけを高速性の根拠にせず、必要性を測ってから索引追加やSQL変更を提案する。今回は実DB索引の再点検や性能目標達成を実施済みと扱わない。

公式仕様：[MySQL 8.4 EXPLAIN / EXPLAIN ANALYZE](https://dev.mysql.com/doc/refman/8.4/en/explain.html)、[SHOW INDEX](https://dev.mysql.com/doc/refman/8.4/en/show-index.html)。EXPLAIN ANALYZEが実行を伴うこと、SHOW INDEXのCardinalityは正確な件数ではなく推定であることに注意する。

## できること

- 所属メンバーは会議を開始できる。開始時の保管されていない案件を、納期・同日のID順で対象として固定する。通常一覧の1ページだけを流用しない。開始後に追加・復元された案件は次の会議から対象にする。
- 対象を自分の画面で選び、前後へ移動できる。確認成功後は次の未確認案件へ進む。他の参加者の選択は変えない。
- 確認した時点で、DBの最新の進捗・状態・案件版・確認者・日時を保存する。会議開始時や未確認の案件には確認記録を作らない。その後の進捗更新で保存した値を上書きしない。
- 会議中に確認を取り消し、最新値で再確認できる。取消前の記録は削除せず、取消者・取消日時を残す。監査履歴を一覧する画面/APIは今回の対象外。
- 画面を閉じても同じ会議を再開できる。再開時は最初の未確認案件を選ぶ。案件選択の位置そのものは個人の画面内状態で、DBに共有しない。
- 全対象から確認済み・未確認件数を算出する。終了前に未確認件数と全一覧を示す。残して終了する場合は明示確認が必要。終了後は確認・取消・進行役変更をAPIでも拒否する。次の会議は確認0件から開始する。
- 進行役は0人または1人。現在の所属者から選び、会議中に交代・解除できる。指定時は進行役本人だけが操作でき、管理者を特例にしない。未指定なら所属者全員が操作できる。

開始後に案件が保管されても、対象を途中で減らさず警告付きで残す判断にした。「新しい会議から外す」という要件に従い、既に始まった会議の対象・件数を保持する。会議は複数作成可能で、チームに進行中1件だけという制約は追加していない。

| `GET /teams/:teamId/meetings/:meetingId` | 全対象、確認時の値、現在値、全件数、操作可否を取得 |
| `PATCH /teams/:teamId/meetings/:meetingId` | `action`、`expectedVersion` と、操作に必要な項目だけを受け付ける |

操作は `confirm` / `unconfirm`（`entryId`）、`facilitator`（`facilitatorUserId`）、`finish`（`allowUnconfirmed`）。進捗や確認者の偽装入力は拒否する。
エラーは既存と同じ `{code,message}`。未認証401、所属/進行権限403、対象なし404、古い版/終了済み/未確認の終了409。入力不正400、本文上限4096バイト超過413、JSON以外415、対象外メソッド405。

会議版を比較する前に会議行をロックし、記録と版更新をまとめる。二人が同じ版で保存した場合は一方を409にする。確認する案件もロックして、その時点の値を読む。保存の最後に失敗した場合は記録も取り消す。

## 2026-11-25：相談・決定・選択的引き継ぎ（現在の実装）

上の「相談・決定・作業項目は未完成」は過去時点の記録。現在は次の範囲をローカル実装し、専用MySQL・実HTTP・Next.js・Chromeで確認した。本番未反映。重要業務の自動優先、独立したタスク画面、通知、添付、会議外での対応事項更新は追加していない。

### 操作と履歴

1. 会議の対象案件を選び、「相談内容」「決定事項」を保存する。どちらも空欄可、各2,000文字まで。
2. 対応内容と現在の所属者を指定して登録する。担当者は必須、期限は任意。状態は未対応・対応済み・取消。完了しても案件の進捗率や状態は自動変更しない。
3. 編集・引き継ぎは既存の進行役だけが行う。進行役を指定しない会議は現在のメンバーが操作できる。管理者や担当者本人への例外は設けない。
4. 次回会議で「引き継ぎ候補を確認」し、必要な事項だけ選択する。元会議が今回の開始前に終了済みであり、本体が今も未対応であることを採用時にも再確認する。自動コピーしない。同一本体・同一案件の会議内二重採用を一意制約で防ぐ。
5. 担当者が退会済みなら現在の所属者へ再割当する。同じ担当者が改名した場合も、採用時の現在名を新しい会議へ記録する（本体版を増やし、他の進行中会議にも差を知らせる）。過去の担当者名はスナップショットに保持する。対応済み・取消済みを古い会議から復活させない。
6. 終了済み会議は閲覧専用。「引き継ぎ元の会議を見る」で元の案件記録へ移動する。本体が後日変化しても、過去の相談・決定・対応事項は変えない。

### DB・競合防止

- `MeetingProjectNote`は会議内の案件1件につき相談・決定のメモ1件。作成者・作成日時と最終更新者・更新日時を保持する。
- `MeetingActionItem`は対応事項の現在値。`MeetingActionSnapshot`は各会議で確認した内容・担当者名・期限・状態・本体版を保持する。引き継ぎ元snapshotへの参照が経路になる。
- 外部キーは「参照先が実在し、同じチーム・案件であること」をDBでも検査する。`teamId`を含む複合キーを使う。一意制約は「同じ会議案件へ同じ対応を2度登録しない」ためのルール。所属を消しても人物と過去名は残す。
- 更新は現在の所属行→会議行→対応事項本体行をロックし、会議版と本体版を照合する。終了と更新も同じ会議行で直列化する。別会議で本体が変わったら古いsnapshotで編集・終了しない。「最新の対応を確認」で明示的に取り込む。
- `ReadCommitted`でロック待機後の最新本体版を読む。本体・snapshot・会議版は1つのトランザクションにまとめ、途中の例外はすべてロールバックする。全競合・高負荷・デッドロックを網羅した保証ではない。

### ReactからMySQLまで

Reactのstateは入力中の下書き、Next.js APIはJSON・本人・所属・進行役の検査、Prismaは条件付き読み書きとトランザクション、MySQLは保存と外部キー・一意制約を担当する。画面の権限表示だけを信用せずAPIでも毎回検査する。

版番号は「読んだときの番号と今の番号が同じなら保存する」という楽観的ロック。番号が違う409では入力を保持し、比較後に明示的に再試行する。自動マージ・自動再送はしない。

10秒の再取得は未保存下書きを上書きしない。未保存時は案件移動・終了・チーム切替・ログアウトを止め、保存または明示的に破棄してから移動する。ブラウザーの戻る／進むも元の表示を維持し、その履歴エントリーのURLを戻す。閉じる・再読込はブラウザーの離脱警告を要求するが、ブラウザーの設定や強制終了まで入力の永続保存を保証しない。下書きをlocalStorageへ保存しない。

`20261124_meeting_records/migration.sql`は3テーブルと制約・索引の追加だけ。既存列・テーブル・業務データを削除しない。Prisma migrationはSQLを履歴ファイルにし、適用した履歴とチェックサムをDBの`_prisma_migrations`へ記録する仕組み。生成・検査とDBへの適用は別の操作。
