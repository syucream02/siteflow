# SiteFlow 学習ガイド

## この作品で目指すこと
現場調査の業務を理解し、画面・業務ルール・データ・品質の判断を説明できる作品を育てます。採用結果は保証できませんが、自分の判断と検証結果を具体的に示す材料になります。

## 初版の範囲
架空の3案件、指摘の登録、担当者・期限・優先度、状態別絞り込み、対応記録、確認依頼・承認・差し戻し、状態変更の履歴を実装。PC・スマホに対応しています。写真、案件の追加、報告書、認証、DB保存は未実装です。データはReactのメモリにあり、再読み込みで初期化します。他のブラウザや利用者と共有しません。

## 技術を選んだ理由
- React：データが変わると一覧や完了率が更新される、状態と画面の関係を学ぶ。
- TypeScript：Issue・Project・Statusの形を定義し、取り違えや存在しない状態を開発時に検出する。ただし外部入力は型だけでは守れないため、実行時検証も必要。
- App Router形式：画面の入口（app/page.tsx）と対話する部分（Workspace）を分ける。今回の実行エンジンはSitesスターターのVinextで、Next.js App Router互換の構造を使っている。通常のNext.js本体での動作保証とは別。就活向けにNext.jsへ移行する場合は、ビルド・SSR・認証をあらためて検証する。
- 既存UI部品：ダイアログのフォーカス制御やEscape、セレクトなどを毎回自作せず、業務に集中する。依存パッケージが多いのはスターター由来で、すべてを学習済みと主張しない。

## ソースを読む順番
1. lib/siteflow/domain.ts：データ型と業務ルール。
2. lib/siteflow/seed.ts：架空の初期データ。ProjectとIssueをIDで結びつける。
3. app/page.tsx：画面の入口。
4. components/siteflow/workspace.tsx：Reactの状態、イベント、表示。
5. app/globals.css：画面幅ごとの配置とフォーカス表示。

最初はWorkspaceを一つにまとめ、追いかけるファイルを増やしすぎない。画面が増えたらIssueForm、IssueDetail、ProjectSummaryに分割する。業務ルールだけは最初から分離し、UIや将来のAPIで重複させない。

## なぜこの業務ルールなのか
未対応 → 対応中 → 確認待ち → 完了。確認待ちから対応中への差し戻しも可能。飛び越しは拒否する。「作業した」と「内容を確認した」を区別するため。確認依頼には対応内容が必須。完了率は完了件数÷指摘件数から計算し、独立した数値として保存しない。指摘0件は0%とする。

日付の期限はYYYY-MM-DD、履歴はタイムゾーンを含む日時。今日の基準は日本時間、期限当日は超過扱いしない。完了済みは期限超過に含めない。UIを隠すだけでアクセス制御したことにはならない。現在はデモの同一利用者が対応・承認できる。

## 小さな練習
1. seed.tsの案件名を変える。なぜ画面に反映されるか説明する。
2. 指摘を登録し、一覧と件数と完了率がどの状態から算出されるか追う。
3. 対応内容なしで確認依頼する。どの関数で拒否されるか確認する。
4. 新しい状態「保留」を入れるなら、型・ラベル・遷移・集計のどこを変えるか先に書く。

## 肉付けする順番
| 段階 | 作るもの | 学ぶこと・完了条件 |
|---|---|---|
| 1（今回） | メモリ上の画面と業務ルール | 登録→対応→確認→完了を実演し、禁止する遷移を説明できる |
| 2 | 通常のNext.js構成の検討、PostgreSQL、API、入力検証、マイグレーション | 再読み込みで残る。存在しない案件や不正入力をサーバーでも拒否 |
| 3 | 認証、企業・案件単位の権限 | 別企業のデータ取得・更新がAPIで拒否される。担当者と承認者の権限を分ける |
| 4 | 写真添付・保存 | 許可する形式・容量・アクセス範囲を定義し、失敗しても再試行できる |
| 5 | 更新競合、監査記録、通知 | 古いversionでの更新を拒否。誰がいつ更新したかサーバーで記録 |
| 6 | CI、E2E、ログ、バックアップ、公開 | クリーン環境で自動検証でき、障害を検知して復旧手順を実演 |

Sitesへの公開と、将来のNext.js・PostgreSQL向けのホスティング選択は別の設計判断。次段階でランタイム・費用・DB接続方法を比較して決める。

## 毎回の進め方
課題 → 受入条件 → 設計の選択肢 → 実装 → 検証 → 判断記録、の順に進める。非機能要件は「速い」「安全」ではなく、条件と確認方法を書く。次の機能を依頼するときは「DB保存を追加して。設計理由と、今回自分が読む場所・練習問題も教えて」のように、一段階ずつ進める。

## 面接で説明する材料
実体験で確認した課題と想定の課題、実装済みと計画、測定値と目標を分ける。認証未実装の段階で「安全なマルチテナントSaaS」とは表現しない。各判断について、選んだ理由・見送った案・弱点・検証結果を残す。
